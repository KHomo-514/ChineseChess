# 中国象棋规则规格与实现对照

本文档记录本模组**实现所依据的规则规格**、**出处**、**实现位置**，以及**已知偏差**。
规则调研来自 WXF（世界象棋联合会）2018 年规则、华语棋界通行的《中国象棋竞赛规则》相关条目与维基百科等公开资料。

> ⚠️ 调研过程中 `web_fetch` 工具不可用（所有域名均报「非公网 IP」），因此**原始 PDF 未能逐字核对**，结论主要来自搜索结果摘要、条目文本与领域知识交叉验证。**未能核实的条目集中在 §5**，请在使用前留意。

## 1. 棋盘几何

- 9 条竖线（路/file，编号 0–8，自红方视角从左到右）× 10 条横线（线/rank，编号 0–9，自红方底线向上）。
- 棋子落在**交叉点**上，共 90 点。无王车易位、无吃过路兵、无升变。
- **九宫**：3×3。红方 = 路 3–5 且线 0–2；黑方 = 路 3–5 且线 7–9。只有这 9 个点。
- **河界**：线 4 与线 5 **之间**的空隙，不是一条可落子的线。**过河**：红子线 ≥ 5；黑子线 ≤ 4。
- 只有车、马、炮、兵（卒）能过河；帅（将）、仕（士）、相（象）永远不过河。

初始摆法（路, 线）：

| 红方 | 黑方 |
|---|---|
| 帅 (4,0) | 将 (4,9) |
| 仕 (3,0) (5,0) | 士 (3,9) (5,9) |
| 相 (2,0) (6,0) | 象 (2,9) (6,9) |
| 马 (1,0) (7,0) | 马 (1,9) (7,9) |
| 车 (0,0) (8,0) | 车 (0,9) (8,9) |
| 炮 (1,2) (7,2) | 炮 (1,7) (7,7) |
| 兵 (0,3) (2,3) (4,3) (6,3) (8,3) | 卒 (0,6) (2,6) (4,6) (6,6) (8,6) |

交叉验证（标准 XQ-FEN）：`rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w`

> 命名坑：XQ-FEN 的 rank 是**自上而下**排列（线 9 在最前），与本文自下而上的线号相反；中文着法的路号红黑各自反向（红用中文数字自右向左，黑用阿拉伯数字自左向右），本模组内部一律使用自红方视角的 0–8 / 0–9，不涉及中文记谱。

**实现**：`board/Squares.java`（索引与地理判定）、`board/Board.java#initial()`。

## 2. 走子

通用合法条件：目标在盘内、目标为空或敌子、所有「阻挡点」为空、**走完后自己的帅（将）不被攻击**。

| 棋子 | 走法 | 阻挡点 |
|---|---|---|
| 帅/将 | 直行一步 `(0,±1) (±1,0)` | 无；且必须留在本方九宫 |
| 仕/士 | 斜行一步 `(±1,±1)` | 无；且必须留在本方九宫 |
| 相/象 | 田字 `(±2,±2)` | **象眼** = 中点 `(±1,±1)` 必须为空；**不可过河** |
| 马 | 日字 `(±2,±1) (±1,±2)` | **马腿** = 2 格方向上的相邻点（`(±1,0)` 或 `(0,±1)`）必须为空 |
| 车 | 直线任意距离 | 中间全部为空 |
| 炮（不吃） | 直线任意距离 | 中间全部为空，且目标为空 |
| 炮（吃） | 直线任意距离 | 中间**恰好一个**炮架（任意颜色），炮架与目标之间全空，目标为敌子 |
| 兵/卒 | 向前一步；**过河后**可左右一步 | 无（向前可吃子，即「直吃」）；永不后退、永不走斜 |

**白脸将 / 对脸（照面）**：两帅（将）不得在同一路上且中间无子。本模组把它建模为**帅（将）沿空直线可以吃对方将**的一条伪合法着法，于是：
- 任何造成对脸的走法，会在「走后自己被将」判定中自动非法；
- 将军检测天然包含它，无需特判。

**炮的最小吃子距离为 2**：相邻位置的炮**永远不能吃子**（没有炮架）。实现按「先找炮架，再过炮架找第一个子」的算法，与该结论一致。

**实现**：`board/rules/` 下每个棋子一个类（`GeneralRule`、`AdvisorRule`、`ElephantRule`、`HorseRule`、`ChariotRule`、`CannonRule`、`SoldierRule`），由 `MoveRules` 汇总并按「走后自己不被将」过滤。

## 3. 终局条件

| 条件 | 判定 | 实现 |
|---|---|---|
| 将军 | 己方帅（将）被敌方攻击。**被牵制的子仍然构成将军**（牵制限制移动，不限制攻击） | `ThreatDetector.isInCheck` |
| **将死** | 被将且无合法着法 → **被将方负** | `XiangqiGame#evaluateOutcome` |
| **困毙 / 欠行** | **未被将**但无任何合法着法 → **该方负**（官方规则，与国象判和不同） | 同上（无着法时按是否被将区分 `CHECKMATE` / `STALEMATE`，两者都是负） |
| **长将** | 同一局面第 3 次出现，且每次都是同一方被将 → **长将方判负** | `PositionHistory#constantlyCheckedSide` |
| 三次重复（非长将） | 判和 | `EndReason.REPETITION_DRAW` |
| **自然限着** | 双方连续 60 回合（**120 着**）无吃子 → 判和；**任何吃子都重置计数** | `RuleSettings#noCaptureDrawPlies`（默认 120，可配置，0 关闭） |
| **双方无取胜可能** | 双方都没有车/马/炮/兵 → 判和 | `Board#hasAttackingMaterial` |

**非法着法**：本模组在走法生成阶段就不产生非法着法（自带「不能送将」「不能对脸」过滤），客户端也只会给出合法落点；服务端仍独立再校验一次，拒绝并回推权威局面。

## 4. `棋例`（重复局面判罚）与本实现的取舍

官方 `棋例` 的完整流程是：同一局面第 3 次出现或形成循环 → 裁判对**双方每一步循环着法**分类为「将/杀/捉/兑/献/拦/跟/闲」→ 按「禁止着法 vs 允许着法」表判定；**禁止方不变则负**，双方都禁止或都允许则**不变作和**。

- **禁止着法（判负）**：长将、长捉、长杀（长要杀）、一将一杀、一将一捉、一杀一捉
- **允许着法（判和）**：长兑、长献、长拦、长跟、长要抽吃、**帅（将）长捉、兵（卒）长捉**、长闲

> 其中「长杀」属于**禁止着法**（不是判和）——这一点在公开资料中容易混淆，已核实。
> 「跟」的定义（《象棋》条目）：*「凡走子盯牵对方有根子而又不具攻击作用者，称为『跟』」*——即**盯住有根子且不构成攻击**才算跟（允许），这正是「捉」与「跟」的分界。

**本模组实现的是行业通行的简化版（c）**：三次重复 + 长将判负。官方与主流引擎的对照：

| 方案 | 说明 | 是否采用 |
|---|---|---|
| (a) 完全不处理重复 | 循环无法终止 | ✗ |
| (b) 单纯三次重复判和 | **把长将（本应判负）变成判和**，让败方得以逃脱，实质性错误 | ✗ |
| **(c) 三次重复 + 长将判负** | 只多记录每步「是否被将」，纯长将情形与官方一致 | **✓ 默认** |
| (d) (c) + 近似长捉 | 需要子力价值 + 有根/无根判断 + 将帅兵卒例外，**既会误判也会漏判** | ✗（有意不做） |
| (e) 完整 `棋例` | 需要对每个循环着法分类 | ✗ |

因此本模组在**长捉 / 长杀**局面下会判「和」而官方裁判会判「负」——这是一个**有界且已知**的偏差，选择它是因为近似实现长捉的误判率高于漏判成本，这也是 Pikafish 等引擎暴露「自动判和」配置而非声称合规的原因。

## 5. 未能核实的条目（请留意）

1. **自然限着的精确数值**（60 回合 = 120 着）：与领域知识及多方摘要一致，但**未能逐字核对 2011 年《中国象棋竞赛规则》原文**。这是最值得再确认的一条（已做成配置项，便于调整）。
2. 长将 / 长捉所用的回合**是否**计入自然限着计数（有资料称排除）。
3. 「长杀」的措辞是「直接判负」还是「须变着、不变则负」——对强制变着的引擎而言两者等价。
4. 各线上平台（如天天象棋）与快棋规则使用的**缩短版限着数**。
5. 「捉」的子力价值阈值（判定有根子是否可捉），仅在实现 (d)/(e) 时才需要。
